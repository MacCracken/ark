# Pre-v1.0 security audit — post-P(-1) surfaces

- **Date**: 2026-06-18
- **Scope**: the surfaces added since the P(-1) audit
  (`docs/audit/2026-04-16-p-1-security-audit.md`) — the `.ark` reader/installer
  (`src/ark_package.cyr`), the marketplace download path (`src/marketplace.cyr`),
  and the shakti execution backend (`src/exec.cyr`).
- **Method**: threat-model the new code against current package-manager 0-day /
  CVE classes (researched 2026-06), then audit each surface and fix the
  exploitable issues.

## Threat landscape (researched 2026-06)

Package managers are a top supply-chain target. The classes that map onto ark's
new surfaces:

- **Archive path traversal / "zip slip" (CWE-22)** — malicious archive entry
  paths (`../`, absolute) write outside the extraction root → arbitrary file
  write → privilege escalation / code execution. Live 2025–26 examples: Argo
  Workflows [CVE-2025-62156], `tar` [CVE-2025-45582], OpenClaw, PaddlePaddle's
  download/extract. Affects tar/zip/jar/etc.
- **Signature-verification bypass / fail-open** — verification skipped when the
  check can't run [CVE-2022-31156], unparseable signature treated as valid
  [CVE-2012-6088], "valid" when a provenance file is simply absent
  [CVE-2026-35205], and the broader Shai-Hulud / TeamPCP npm+PyPI worm campaigns
  (2025–26) where even *validly provenance-signed* artifacts were malicious
  because the signer itself was compromised — i.e. a signature without a **trust
  anchor** proves nothing about publisher identity.
- **Decompression bombs (CWE-409)** — a tiny compressed payload declaring a huge
  uncompressed size exhausts memory. 2025 examples: Redlib DEFLATE bomb
  [CVE-2025-30160], OpenTelemetry Collector [CVE-2024-36129], unfurl zlib
  (~1000:1 ratios). Mitigation: cap/stream the output size before allocating.
- **Out-of-bounds reads on malformed binary input (CWE-125)** — length/offset
  fields from an untrusted container drive reads past the buffer.

## Findings

| # | Finding | Class | Severity | Status |
|---|---|---|---|---|
| 1 | `.ark` installer wrote files at attacker-controlled paths with no traversal check | CWE-22 zip-slip | **HIGH** | **Fixed** |
| 2 | `.ark` reader allocated `u_len` (attacker u64) with no cap | CWE-409 bomb | **MED** | **Fixed** |
| 3 | `.ark` reader read index/manifest/data lengths with no bounds check | CWE-125 OOB read | **MED** | **Fixed** |
| 4 | Signature verified against the package's **own embedded pubkey**; unsigned packages accepted | trust anchor / fail-open | **HIGH** | **Open — documented** |
| 5 | Symlink entries: target not constrained (symlink-then-write-through) | CWE-22 (variant) | **MED** | **Open — documented** |
| 6 | TLS/transport + publisher-keyring trust delegated to sandhi/mela | dependency trust | **INFO** | Noted |

### 1. Zip-slip in the installer — FIXED
`ark_pkg_install` built each on-disk path as `install_root + entry_path` and
wrote it with no validation; a `.ark` entry path like `/../../etc/cron.d/x`
escaped the root → arbitrary file write. **Fix:** `apkg_path_safe()` requires a
leading `/` and rejects any `..` path component; `ark_pkg_install` **pre-scans
every entry and aborts before writing anything** if any path is unsafe.
Regression-tested (`test_pkg_security`).

### 2. Decompression bomb — FIXED
`alloc(u_len)` used the file's declared uncompressed size directly. **Fix:**
reject `u_len > ARK_MAX_DATA` (256 MiB) before allocating, and require the
compressed bytes to fit within the verified prefix.

### 3. Out-of-bounds reads — FIXED
The manifest length, per-entry `path_len`/`target_len`, and data `c_len`/`u_len`
were used to `memcpy`/`str_new`/`hex_encode` with no bounds check. **Fix:**
every variable-length read is now bounded by `r` (the SHA-256-verified prefix
length); the per-file hash loop checks each payload lies within the inflated
buffer. A malformed/truncated `.ark` is rejected (returns 0), not crashed.

### 4. Signature has no trust anchor; unsigned accepted — OPEN (documented)
`ark_pkg_read` verifies the Ed25519 signature against the pubkey **embedded in
the package itself**, and accepts packages with the signed flag clear. So the
signature proves only "not modified after signing" — **not** that a *trusted
publisher* signed it (an attacker self-signs with their own key, or strips the
signature). This is the Shai-Hulud / fail-open class.
**Recommendation (pre-1.0):** verify against a **trust anchor** —
mela's publisher keyring / transparency log (mela 1.0.0 ships `mela_keyring_*`)
or a configured ark trust store — and add a config policy to **require a valid
signature from a trusted key** for untrusted sources (marketplace), failing
**closed**. Tracked as a v1.0-criterion item ("package signing verified
end-to-end").

### 5. Symlink target not constrained — OPEN (documented)
Entry *paths* are now traversal-checked, but a symlink entry's *target* is not:
a `.ark` could create `link → /etc` then write `link/x`, escaping via the
symlink (`file_write_all`/`mkdir_parents` follow it). **Recommendation:** write
with `O_NOFOLLOW`, refuse to traverse a symlinked parent, or reject
absolute/`..` symlink targets. Lower severity than #1 (multi-step, and the link
location itself is now confined).

### 6. Transport + keyring trust delegated — INFO
ark fetches via mela's client over sandhi (TLS); certificate validation is
sandhi's responsibility, and publisher trust is mela's keyring/transparency
model. ark should consume those (see #4) rather than re-implement, but should
not *weaken* them — today it bypasses the keyring by doing its own
embedded-pubkey check.

## Outcome

Three exploitable memory-safety / file-write issues (#1–#3) are **fixed and
regression-tested**; the valid-package path is unaffected (280 tests pass; the
563-recipe zugot corpus still parses). The two trust-model items (#4, #5) are
**documented with recommendations** and feed the remaining v1.0 signing
criterion — they are the gating work before ark installs from untrusted
marketplaces in production.
